# monitoring

Лёгкий мониторинг одной Linux-виртуалки: Python-сборщик → публичные JSON в S3 →
статическая страница на GitHub Pages. Сбор метрик и чтение S3 отключены по умолчанию
и включаются явно в конфигурации.

## Почему собственный сборщик

Для этих нескольких метрик достаточно стандартной библиотеки Python и Linux
`/proc`, `/sys`, `statvfs`: не нужны Docker, sysstat, Prometheus или веб-сервер на
виртуалке. Сборщик не перечисляет процессы и не запускает внешние команды.
Зависимость boto3 нужна только отдельной короткоживущей команде выгрузки.
Лимиты CPU и памяти задаются в unit-файлах systemd; их можно подобрать под сервер
после измерения фактического потребления ресурсов.

## Локальная проверка и демо

Python 3.10+; для сбора нужен современный Linux с `MemAvailable` в `/proc/meminfo`.
Статус, тесты и страница работают также на macOS.

```sh
cp .env.example .env
chmod 600 .env
python3 -m agent status
python3 -m agent run
python3 -m agent upload
python3 -m unittest discover -s tests -v
```

Команды `run` и `upload` при `MONITOR_ENABLED=false` ничего не делают.
`status` не показывает ключи, endpoint или содержимое `.env`.

Для просмотра интерфейса:

```sh
python3 -m http.server 8090 --bind 127.0.0.1 --directory web
```

Открыть `http://127.0.0.1:8090/` — выключенная страница;
`http://127.0.0.1:8090/?demo=1` — явно обозначенные **вымышленные данные**,
создаваемые в браузере. Демо не включает сборщик, не читает Linux-метрики и не
обращается к S3. Никакие внешние CDN, шрифты и аналитика не используются.

Дополнительная проверка интерфейса, если установлен Playwright и Chromium:
`node tests/browser.mjs`. Она поднимает временный localhost-сервер, проверяет
выключенную страницу, демо, ширины 390/1440 px, чтение часовой/дневной истории,
неизвестные значения, устаревшие данные и HTTP-ошибку. S3 подменён локальными
перехватами запросов браузера; реальных обращений к хранилищу нет.

## Какие данные публикуются

Схема задана явным списком в `agent/metrics.py`. Любое лишнее поле, строковое
значение, NaN или Infinity отклоняется до записи и перед экспортом.

| Поля | Смысл |
| --- | --- |
| `ts`, `interval_s` | UTC Unix-время конца измерения и фактический интервал |
| `cpu_busy_pct` | user + nice + system + irq + softirq, от всех CPU, 0–100% |
| `cpu_user_pct`, `cpu_system_pct` | пользовательские и системные вычисления |
| `cpu_iowait_pct`, `cpu_steal_pct` | отдельно ожидание I/O и отнятое гипервизором CPU-время |
| `load1`, `load5`, `load15` | load average; это не проценты CPU |
| `mem_total_bytes`, `mem_available_bytes` | всего RAM и доступно, с учётом освобождаемого кэша |
| `swap_total_bytes`, `swap_used_bytes` | всего и занято swap |
| `net_rx_bytes_s`, `net_tx_bytes_s` | суммарная скорость выбранных внешних интерфейсов |
| `disk_read_bytes_s`, `disk_write_bytes_s` | суммарный I/O выбранных блочных устройств |
| `disk_total_bytes`, `disk_available_bytes` | ёмкость и доступное место выбранной файловой системы |

Нет IP, hostname, имён интерфейсов/дисков, путей, команд, процессов, пользователей,
логов и переменных окружения. Эти имена могут присутствовать в локальной настройке,
но в документы не попадают. Публичными остаются профиль нагрузки и время измерений.

При сбросе счётчиков, смене интерфейса или отсутствии устройства скорость равна
`null`, а не нулю/скачку. Первый интервал после старта снимается двумя измерениями;
после перезагрузки не вычисляются разности со счётчиками прошлой загрузки.
Устройство диска определяется по файловой системе `MONITOR_DISK_PATH`, для раздела
используется весь родительский диск. Для LVM/RAID/overlay или нескольких физических
дисков лучше задать `MONITOR_DISK_DEVICES` явно, не включая одновременно диск и его
раздел/дублирующие слои. Без подходящего устройства I/O останется `null`.
Внешние интерфейсы определяются по default route IPv4/IPv6. Для VPN, bonding и
нестандартной маршрутизации задайте `MONITOR_INTERFACES` явно, без дублирования слоёв.

## Буфер, файлы и ошибки

- Сбор каждые 15 секунд, без сети, в SQLite WAL; отдельный процесс выгрузки раз в минуту.
- Локальный буфер по умолчанию 7 суток плюс текущий UTC-день. Старые полные дни
  удаляются даже если их не удалось выгрузить: длительный обрыв не заполнит диск
  бесконечной очередью. SQLite повторно использует освобождённое место; файл может
  оставаться на достигнутом размере.
- Неудачная отправка не подтверждает очередь. Следующий запуск повторяет PUT.
  Изменившийся во время загрузки час также остаётся в очереди.
- Отдельные файловые блокировки предотвращают два сборщика или два экспортёра.
- При перегрузке пропущенные интервалы не подменяются нулями. Измерение после
  задержки содержит фактический интервал; подробность внутри него восстановить нельзя.
- Отправляются только изменившиеся часы и соответствующие дневные агрегаты.
  Очередь обрабатывается с новых часов, максимум 12 за запуск.

```text
<S3_PREFIX>/latest.json
<S3_PREFIX>/hours/YYYY-MM-DD/HH.json
<S3_PREFIX>/days/YYYY-MM-DD.json
```

Все документы: `schema: 1`, `Content-Type: application/json`, `Content-Encoding: gzip`.
Ключи заканчиваются `.json`: браузер автоматически распаковывает тело по заголовку.
Часовой документ содержит `resolution_s` и `samples` с исходными измерениями.
Дневной — пятиминутные средние, взвешенные фактическими интервалами (вес до 300 с),
плюс `count`, `cpu_peak_pct`, `mem_available_min_bytes`. Пятиминутный bucket
определяется временем конца измерения; границы не интерполируются.
`latest.json` содержит `sample_interval_s` и последний `sample`.

За сутки страница читает часовые документы, за неделю/месяц — дневные. Чтение
ограничено четырьмя параллельными запросами. Исторические документы кэшируются в
памяти страницы до 15 минут; «Обновить» очищает кэш (полезно после догрузки).
Автообновление при скрытой вкладке приостанавливается.

Штатный режим — примерно **3 PUT в минуту**, то есть 129 600 за 30 суток:
текущий час, текущий день, последнее значение. При догрузке и пересечении часа/дня
больше. Стоимость зависит от провайдера: нужны тарифы на PUT/GET, хранение и трафик.
При включённом versioning каждое обновление создаёт версию; lifecycle-шаблон
содержит очистку старых версий. Он ничего не применяет автоматически.

## Установка и настройка

1. Подготовить Linux-сервер с Python 3.10+ и systemd.
2. Создать отдельный S3 prefix и отдельный ключ с `PutObject` только в него.
   Экспортёр не требует List, Get, Delete, ACL, администрирования bucket.
3. Заполнить `.env` по `.env.example`, оставив переключатель выключенным до конца
   настройки. Значения читаются как текст, без `source`, shell expansion или `eval`.
   Переменные окружения процесса имеют приоритет; относительный STATE_DIR отсчитывается
   от каталога `.env`. Права локального файла — `0600`.
4. Установить зависимости в venv:

   ```sh
   python3 -m venv .venv
   .venv/bin/python -m pip install -r requirements.txt
   ```

5. Подготовить S3 read policy, CORS и lifecycle из `deploy/*.example.json`, заменив
   placeholders. Политики — AWS-формат; совместимость и публичный HTTPS URL зависят
   от провайдера. CORS origin — `https://USER.github.io` без пути репозитория,
   либо точный origin собственного домена. CORS сам по себе не даёт публичный доступ.
   Шаблоны нужно **объединить с существующей конфигурацией**, не затирая её целиком.
   Не открывать весь bucket, если там есть другие данные.
6. На Linux разместить исходники в `/opt/monitoring`, создать системного пользователя
   `monitoring` без входа. `.env` должен читаться этим пользователем (например,
   владелец `monitoring:monitoring`, права `0600`). systemd хранит данные в
   `/var/lib/server-monitoring`; это явно переопределяет значение из `.env`.
7. Просмотреть unit-файлы `deploy/`, скопировать в `/etc/systemd/system/`, выполнить
   `systemctl daemon-reload`. Само копирование не включает службу и таймер.
8. Для включения сбора поставить `MONITOR_ENABLED=true`, запустить
   `python3 -m agent once` и `.venv/bin/python -m agent upload`, проверить содержимое
   трёх публичных документов и фактическое потребление CPU/RAM. На systemd-хосте
   ручные команды нужно запускать от `monitoring` с
   `MONITOR_STATE_DIR=/var/lib/server-monitoring`, чтобы использовать ту же базу.
9. Затем `systemctl enable --now monitoring-collector.service monitoring-upload.timer`.
10. В настройках GitHub-репозитория открыть Settings → Secrets and variables →
    Actions → Variables. Добавить `MONITORING_DATA_URL` — публичный HTTPS URL prefix,
    и, при необходимости, `MONITORING_TITLE` — подпись сервера.
    В GitHub Pages выбрать GitHub Actions и вручную запустить workflow.
    Он создаст публичный `config.js` из этих переменных; без URL страница выключена.
    Исходный `web/config.js` остаётся общим и подходит для локального демо.
    В артефакт Pages попадает **только `web/`**, не исходники, `.env` или база.

Для выключения: `MONITOR_ENABLED=false` предотвращает запуск новых команд.
Уже работающий сборщик читает настройки только при старте, поэтому его нужно остановить:

```sh
sudo systemctl stop monitoring-collector.service monitoring-upload.timer monitoring-upload.service
sudo systemctl disable monitoring-collector.service monitoring-upload.timer
```

Удалить переменную репозитория `MONITORING_DATA_URL` и опубликовать страницу, если
нужно также остановить чтение S3 из браузера. При самостоятельном хостинге вместо
workflow можно изменить `enabled` в `web/config.js`. Сохранённая публичная история
сама не исчезает.

## Локальные файлы и секреты

`.env`, `.venv`, `state/`, логи, ключи и кэши исключены через `.gitignore`.
В репозитории хранится `.env.example` с шаблоном настроек. Реальные реквизиты S3,
метрики и артефакты предпросмотра не следует добавлять в Git.

`web/config.js` публикуется вместе со страницей: в нём должны находиться только
параметры интерфейса, публичный адрес чтения и подпись сервера. Ключ записи S3
хранится в `.env` на сервере.
